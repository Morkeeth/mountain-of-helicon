## The join, and the key that was missing

The point of the salvage:

```
work_skill_reviews  →  which skill was actually LOADED (content_hash over the bytes)
work_wagers         →  the human's claim and its resolved outcome
task_runs           →  the run
run_cards           →  what it cost and whether it verified
```

That chain reached `task_runs` and **stopped**. `run_cards.run_id` is a
start-clustered string (`run-2026-07-13T22:16`, `runs.py:174`); `task_runs.id` is
an opaque token (`tr_4cba36cdcdf8`). No foreign key, no shared column, and no code
in Mountain joined them. The cost half of lift was unreachable.

**Ruled: an explicit key.** `task_runs.run_id`, added by additive `ALTER` in
`db.py`, stamped at capture and never inferred.

**Rejected: a time-window join** matching `task_runs.execution_started_at` inside
`run_cards[start,end]`. It needed no schema change and would have backfilled the
existing rows — all **three** of them. In exchange it would have left a permanent
code path capable of emitting an approximate lift number. A tool whose entire claim
is that it refuses to fabricate cannot ship a fuzzy join inside the one command
that answers "is this making me better". Runs captured before the column stay
`NULL` and are **reported as unjoinable, never guessed**.

## `helicon lift <skill>`

One command, one question. It reports what it can prove and refuses the rest:

```
$ helicon lift stranger
  LIFT  stranger

  insufficient — no number is honest yet.
  0 run(s) used stranger and 0 did not; 3 per arm are required before a number means anything.

  An empty store reports CLEAN, not healthy.
```

That is the live store's real answer today, and it is the correct one. Below
`LIFT_MIN_RUNS_PER_ARM = 3` per arm it never prints a lift. `tests/test_skill_lift.py`
covers both branches, including that an empty store returns `insufficient` rather
than `0.0`, and that unjoinable runs are counted and named.

**The real gate is not the join — it is capture volume.** The live store holds
**3 `task_runs` against 24 `run_cards`**. The capture protocol is barely used. A
perfect join over three runs answers nothing, so the next move is making capture
happen as a by-product of real work rather than an act of discipline.

Sanity-check shape (do **not** import these numbers as truth): the synthetic
harness at `~/.claude/skill-benchmarks/2026-08-10-lift/RESULTS.md` measured 24
matched with/without runs — `stranger` +0.19 pass / +7.7% tokens, `design-taste`
+0.19 / +24.0%, `eval` and `frame` neutral. `helicon lift` should eventually
produce that *shape* of answer from live work.

## Two defects found by the salvage, in shipping code

**1. Unescaped FTS5 query — fixed.** `search_cubes` passed the caller's string
straight into `MATCH`. `search_cubes("definitely-not-in-demo")` raised
`no such column: not`: FTS5 read `NOT` as its operator and `in`/`demo` as columns.
`build_packet` swallowed the error, fell through to a keyword path, and froze **11
unrelated memories** into a context packet labelled `keyword:definitely-not-in-demo`.
Each token is now quoted (embedded quotes doubled) and joined with `OR`, so a
sentence objective still retrieves and no input can be executed as syntax.

**2. Retrieval has no relevance floor — NOT fixed, recorded.**
`taskrun._candidates` delegates to `snapshots._retrieve`, whose semantic branch
always returns its nearest *k*. An objective matching nothing still freezes 11
memories, and an agent is handed them as its context. Adding a similarity
threshold changes ranking everywhere and is not an additive salvage change.
`tests/test_wager.py::test_attention_queue_flags_a_frozen_but_empty_context_packet`
is marked `xfail(strict=True)` with this reason — **strict**, so the moment a floor
lands the suite fails and the marker must be removed. **Unruled: Oscar's call.**
