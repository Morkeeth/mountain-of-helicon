**Date:** 2026-08-24 · **Branch:** `hackathon/adk-cloud` · **Status:** pre-launch, wedge unbuilt.
**Grounding rule:** every claim below was verified at the object (code read + commands run on 2026-08-24), or it is labeled *claimed / unverified*. Nothing here is inflated.

---

## 1. One-liner + the problem

**Helicon answers one question a coding agent cannot ask for itself: "does this repo's CLAUDE.md lie to me?" — and proves the answer with the command and stdout that settle it.**

Every session, a coding agent loads `CLAUDE.md` / `AGENTS.md` / `.cursorrules` as fact. When those files drift — a moved doc, a renamed script, a retired build step — the agent acts on the lie and neither the agent nor the human finds out. The file still *reads* authoritative.

**Who feels it, how bad — measured, not asserted:**

- An ETH Zurich study (SRI Lab, Gloaguen et al., *"Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?"*, ICSE 2026) tested four agents on SWE-bench-style repos: **LLM-generated context files cut task success by 2–3% while raising cost >20%** (more steps per task). Even developer-written files bought ~4% success at up to +19% cost. Context is not free; a *wrong* context file is a net negative that hides.
- An empirical study of 2,303 context files across 1,925 repos (arXiv:2511.12884, *"Agent READMEs"*) found these files "evolve like configuration code through frequent, small additions" — and that **75.9% of context files include test/build procedures**. That is the single most common instruction type, and it is exactly the executable claim that goes stale silently: a documented `npm run build` or test command that no longer resolves or no longer passes.

The gap: three-quarters of these files carry executable claims, and nothing on the market *runs* them to check they are still true.

## 2. The day-two user (not a judge)

**A senior/lead engineer on a team that runs 2+ coding agents (Claude Code, Cursor) against a shared repo, who owns the `CLAUDE.md`.**

Why they run it weekly (and in CI on every PR):
- Their `CLAUDE.md` is edited by humans *and* by agents (`/init`), grows every week, and rots the way config rots — one line at a time. They cannot eyeball 400 lines for a moved path.
- When an agent burns 20 tool calls hunting a file that was renamed three weeks ago, that is real money and a real wrong turn — and today nothing flags it.

**First 60 seconds (verified, run today):**
```
$ python3 -m helicon.review ~/their-repo

  ❄ HELICON  reviewing their-repo
  ✗ Your setup lies to its agent in 5 places.
    ✗ CLAUDE.md:3  points at docs/ARCHITECTURE.md  — not in this repo
    ✗ CLAUDE.md:4  runs script 'scripts/seed.py' not in repo
    ✗ CLAUDE.md:6  runs no 'build' in package.json scripts
  GRADE F   ·   5 references checked, 5 broken
  An agent that trusts this file walks into 5 dead ends.
```
No key, no config, no LLM, no install of a model. A graded verdict with file:line evidence in seconds. That is the hook. The weekly habit is the CI gate (§6).

## 3. What exists today (verified) vs claimed-but-not-wired

### Verified working (run on 2026-08-24)

| Capability | Where | Evidence |
|---|---|---|
| **`python3 -m helicon.review <repo>`** — ranked, colored, graded stranger review | `helicon/review.py` | Ran on self (GRADE A, 15 refs) and on a seeded broken repo (GRADE F, 5 findings). Exit 1 on rot. |
| **R13 — pointer existence check** | `helicon/pointers.py` | 5 pointer shapes (`@import`, md-link, `[[wikilink]]`, backtick path, bare path) resolved against the live tree. Negation-aware ("X is *no longer* here" is not a broken pointer). |
| **R14 — command name-resolution check** | `helicon/commands.py` | `npm run X` → package.json scripts; `make X` → Makefile targets; `python -m pkg` / `./script.sh` → file exists. Only deterministically resolvable shapes graded. |
| **`helicon ci --path <repo>` + rot exam** | `helicon/cli.py:2323`, `helicon/rot.py` | Ran on the broken repo: printed `CONTRADICTED CLAUDE.md:3 [path] · $ git ls-files -- docs/ARCHITECTURE.md · (no output)` plus the 13-class exam. Exit non-zero on rot. |
| **The narrow execute lane** | `helicon/probes.py:_probe_command` | Runs **read-only git only** (`git log/grep/ls-files`) and compares a *stated count* in the doc to the real count. Plus `chain` (on-chain address) and `killswitch` probes. |
| **GitHub Action manifest** | `action.yml` | Exists and wires `helicon ci`. *Not run in this review — claimed, not verified end-to-end.* |

### The honest shape of the shipped review

`helicon.review` = **existence tier only.** It proves a *path resolves* and a *command name is defined*. It does **not** run `npm run build` or the test suite and check they pass. The only execution anywhere in the codebase is `_probe_command` (git-count comparison) and chain probes — neither runs the documented build/test. **Execute-and-compare on build/test does not exist yet.** It is §5/§6, not the product.

### Claimed but not wired (defects found today)

- **`helicon review <path>` is broken.** Two `cmd_review` definitions collide in `cli.py` (line 610 and line 3538); the last wins (the new repo-review), but the argparse subparser still carries the *old* review's flags (`--batch`, `--terminals`) and defines **no positional `repo` arg**. So `helicon review` works on the cwd but `helicon review .` errors with `unrecognized arguments: .`. Only `python3 -m helicon.review <repo>` accepts a path. This must be fixed before the review is the front-door command.
- **`helicon ci` conflates the target repo with the local store.** On `--path /tmp/test` it printed `Found 80 raw items` and R3/R11 `ROT FOUND` — those came from scanning *this machine's* connectors, not the target repo. The clean stranger-review is `python3 -m helicon.review` (repo-only); `ci`'s exam mixes in local memory-store rot.
- **The `_BASIS` footer misquotes its own source.** `review.py` prints "75.9% of agent context files carry test procedures **that rot**." The paper (2511.12884) says 75.9% *include* test procedures. The lie-detector's basis line overstates. (One-line fix, separate commit.)
- **README describes a much larger product** (memory governance, 23 MCP tools, dashboard, Qwen judging) that is real but is a *different, older* surface. For the wedge, that is scope noise.

## 4. The wedge vs competitors

The existence tier is **commoditized**, confirmed today:

- **ctxlint** (YawLabs) — npx + CI Action + MCP server. Lints CLAUDE.md/AGENTS.md/GEMINI.md/.cursorrules and "catches stale file references, **dead build commands**, hardcoded secrets… cross-references them against your actual codebase." This is `helicon.review` (pointers + commands), already shipped as a product with a one-liner install.
- **agents-lint** (cited in `pointers.py` docstring) — flags dead paths in AGENTS.md/CLAUDE.md.
- **cclint** (carlrannaberg / felixgeelhaar) — config quality + conventions + LSP.

**These check that a reference EXISTS. Helicon's defensible lane is to prove the claim is TRUE — run the documented build/test and compare the result.** ctxlint checks that `npm run build` is *defined*; it does not run it and prove it *passes*. When a doc says "tests pass with `pytest -q`" or "build with `make release`", only execute-and-compare settles whether that sentence is still true. That is the 75.9%-of-files surface nobody else touches — and it is exactly where Helicon already has the machinery (`probes.py` subprocess runner, evidence receipts) but has only pointed it at git so far.

One line: **they lint the map; Helicon drives the road.**

## 5. The ambitious vision (the company, not the CLI)

**CI for agent context — the build gate that keeps every AI agent's instructions provably true against the running system.**

If the wedge lands, Helicon is the layer that makes agent context files *executable specifications*, not prose:

1. **Every claim in a context file becomes a probe.** Paths (done), command names (done), then build/test outcomes, version pins vs lockfile, framework claims vs manifest, API-shape claims vs code. A `CLAUDE.md` that says "we use React 18" fails the moment `package.json` says 19.
2. **The gate moves left.** From a manual weekly scan → a PR check that fails the build when the docs drift → a pre-prompt doorway that warns the agent *before* it acts on a stale line (the `doorway` hook already exists in the older surface).
3. **Fleet/team scale.** One dashboard across every repo an org's agents load; a leaderboard of which context files rot fastest; drift trends over time. The `board`, `leaderboard`, and `measure` surfaces are early versions of this.
4. **The moat is the evidence corpus.** Every probe run is a labeled example of "doc said X, system said Y." That dataset — real drift, machine-verified — is what a linter that only checks existence can never accumulate.

The buyer is a platform/DX team standardizing agent use across an org; the wedge SKU is the free npx + paid CI/dashboard, the same shape ctxlint is already proving demand for one tier down.

## 6. Build plan — ordered slices to the wedge

Each slice is independently shippable and verifiable.

**Slice 1 — HIGHEST LEVERAGE: execute-and-compare for build/test.**
Extend `probes.py` beyond git: when a context file documents a build/test command *with a claimed outcome* ("`pytest -q` passes", "`npm run build` succeeds"), run it in a sandboxed subprocess (timeout, no network, opt-in per command) and grade UPHELD / CONTRADICTED / UNVERIFIABLE on the real exit code + output. Surface it as a new probe kind in `helicon.review`. **This is the wedge; nothing else matters until it exists.** Done-when: a repo whose `CLAUDE.md` claims a passing test that actually fails prints CONTRADICTED with the stderr as the receipt.

**Slice 2 — framework/version claim vs lockfile/manifest.** "We use React 18 / Python 3.11 / Node 20" graded against `package.json`, `uv.lock`, `pyproject.toml`, `.nvmrc`. Deterministic, no execution, high signal, zero false-positive risk. Extends R13 cheaply.

**Slice 3 — fix the front door.** Resolve the `cmd_review` collision, give the subparser a positional `repo` arg, so `helicon review <path>` is the one command. Fix the `_BASIS` misquote. Small, but the CLI is unshippable until `helicon review .` works.

**Slice 4 — the CI gate as the product.** Harden `action.yml`: PR annotations at file:line, a job-summary table, `fail-on: rot|execute|none`. Make the target-repo scan clean (don't mix in the local store — see §3 defect). Done-when: a PR that adds a dead path or a failing documented test turns the check red with the evidence inline.

**Slice 5 — distribution / install story.** Today distribution is `git clone && pip install -e .` — a launch blocker. Ship `npx helicon-review` (the ctxlint shape) as the zero-friction entry, and the GitHub Action as the weekly-habit entry. Done-when: a stranger runs one line, no clone, and gets a graded review.

## 7. Honest gaps + risks

- **The wedge is not built.** The shipped review is the commoditized tier (existence). If we launch on that alone, we are a slower, un-installed ctxlint. Slice 1 is existential, not incremental.
- **The two-Helicons mess.** `~/CODE/helicon` (frozen) vs `~/CODE/mountain-of-helicon` (active); the active repo's README describes a large older memory-governance product, and the review lane is a thin new module inside it. A stranger cannot tell what the product *is*. The launch surface needs to be the review, with the rest as "lab."
- **No install story.** `pip install -e .` from a clone, plus a hard `check_python.py` preflight (stock macOS python is 3.9 and fails). Competitors are `npx`-first. Until Slice 5, adoption friction is fatal.
- **Existence tier has a real, shipping competitor** (ctxlint: npx + Action + MCP). We are behind on the commoditized tier and must not fight there.
- **Execute-and-compare has a safety surface.** Running a stranger repo's documented commands means sandboxing, timeouts, network denial, and opt-in per command. This is the hard part of Slice 1 and the reason competitors stopped at name-resolution — which is also why it is the moat.
- **`helicon ci` scan hygiene.** It currently scans local connectors alongside the target repo; the graded output for a *stranger's* repo must be repo-only or the verdict is polluted.
